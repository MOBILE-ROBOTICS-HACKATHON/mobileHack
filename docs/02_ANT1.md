# Olive olixBot ANT1: our robot reference

Everything here was measured on our ANT1 (10 Oct 2026) or taken from the [Olive docs](https://docs.olive-robotics.com/Products/olixBot%E2%84%A2ANT1-ProUltra/SoftwareDevelopment).

## 0. Connect (Ethernet, your laptop)
1. HOST: the robot's LAN port goes to your laptop. Your Ethernet (`enp2s0`) must be `192.168.7.200/24`; the robot is `192.168.7.100`. Check: `ping 192.168.7.100`.
2. Power-on order: e-stop **pressed**, power button, wait ~10 s, release the e-stop. This stops the lidars browning out at boot. Green LED = ready, red = e-stop, blue = joystick mode, orange corners = laser safety stop.
3. CONTAINER (every terminal; open with `./docker/run.sh`, more with `./docker/exec.sh`; GUI windows appear on your screen): `source scripts/ant1_env.sh`. This sets domain 0, CycloneDDS pinned to `enp2s0`, `$NS`, and the helpers `ant1_teleop` and `ant1_param`.
   - If the robot is reached some other way: `ANT1_IFACE=<iface> source scripts/ant1_env.sh`.

## 1. Step 1: connect and command
```bash
ros2 topic list | grep $NS                       # ~48 topics
ros2 topic echo --once $NS/battery               # %; also $NS/ems (true = e-stop active)
ros2 topic pub --once $NS/s1/bl/user/led_rgb std_msgs/msg/Float32MultiArray "{data: [1.0, 0.0, 0.0]}"   # back-left LED red (fl/fr/bl/br; bm not settable)
ros2 topic pub -r 10 $NS/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.1}}"   # forward; Ctrl-C = stop
#   linear.y = sideways (mecanum), angular.z = turn. Start at 0.1 m/s, e-stop in reach.
ant1_teleop                                      # keyboard; Shift+keys strafe
ant1_drive -p vx:=0.1 -p secs:=2.0               # our node (team_pkg): timed move, clamped, zeros on exit/Ctrl-C
ant1_drive -p demo:=true                         # fwd, back, left, right, turn L, turn R (20 cm each)
ant1_param laser_safety_distance_cm              # built-in stop zone (19 cm); set: ant1_param laser_safety_distance_cm 25
```
Joystick: hold **L1** for manual mode. LB+X for 3 s toggles laser safety (e-stop LED white = on, orange = off). Safety re-enables on every reboot.

### Over Wi-Fi instead of the cable (no SSH needed)
**Robot side first (found 10 Oct): out of the box the ANT1's ROS does NOT use Wi-Fi.**
- Its CycloneDDS config lists only `lo` and `eth0`, and the `wlan0` line is commented out. The original is saved in [ant1_cyclonedds_original.xml](ant1_cyclonedds_original.xml).
- Ping, the Web UI and rosbridge (:5001) work over Wi-Fi, but ROS 2 topics don't, until `wlan0` is enabled in that file:
  - Web UI → Configuration. If it asks, sync the time first ("Yes, sync temporarily").
  - Then Restart Services or reboot.
- **This is hackathon hardware: ask a mentor before editing.**

**After enabling `wlan0` on the robot, the phone hotspot worked** (tested 10 Oct: 48 topics, scan, odom and TF at 10 Hz) with `ANT1_IFACE=wlp3s0 source scripts/ant1_env.sh`. If a network does drop multicast, add the robot's IP so discovery goes unicast: `ANT1_IFACE=wlp3s0 ANT1_PEER=<robot-wifi-ip> source scripts/ant1_env.sh`. That also tested OK.

**Which network.** The robot needs a network that (1) uses a plain SSID + password (WPA2-PSK), (2) lets devices talk to each other, including multicast, and (3) ideally holds only your devices.
- **Eduroam fails all three**, and so does most venue Wi-Fi.
- **A. Phone hotspot (recommended):** laptop and robot both join it, and the laptop keeps internet. On iPhone, enable "Maximize Compatibility" (2.4 GHz).
  - Laptop: `nmcli device wifi connect "<phone-ssid>" password "<pw>"`.
  - Robot: Web UI steps below, choosing the phone's SSID.
  - Robot IP: shown on the Web UI network page, or in the phone's device list.
  - If ping works but there are no topics, first check the robot's DDS config has `wlan0` (above), then try `ANT1_PEER`. Only if that fails, use B.
- **B. Laptop hotspot + phone USB tethering for internet:** the most reliable option for ROS. Steps below.
- **C. Stay on the cable:** the best choice while developing (no dropouts). Wi-Fi is only needed when the robot must go beyond the cable.
- **On a shared network, every ANT1 may be `id001` on domain 0, so your `cmd_vel` could drive other robots.** Change the domain ID on the robot's Web UI (Network and ROS 2 Settings) first.

**Steps for B (laptop hotspot).** For A, skip step 1 and pick the phone's SSID. Robot stationary; the e-stop stays in reach for the whole session.
1. HOST: optional internet first: phone on USB with USB tethering on. Then start the hotspot. This drops eduroam or phone Wi-Fi on this card; run `nmcli connection up eduroam` later to go back.
   ```bash
   nmcli device wifi hotspot ifname wlp3s0 ssid ant1-net password 'pick-8+-chars' band bg
   ```
   Your laptop becomes `10.42.0.1`, and devices that join get `10.42.0.x`.
2. **Keep the Ethernet cable plugged in.** In a browser, open **http://192.168.7.100/network** → **Wi-Fi Configuration**:
   1. Enable `wlan0`.
   2. **Scan SSIDs**, then select `ant1-net` and type the password.
   3. **Test**, then **Apply & Restart**.
   - Address Mode stays DHCP.
   - Only one Web UI session at a time. If there's no Wi-Fi section, ask a mentor.
3. HOST: find the robot's Wi-Fi IP and check it:
   ```bash
   ip neigh show dev wlp3s0
   ping -c 3 10.42.0.X
   ```
   The Web UI also answers at `http://10.42.0.X`.
4. **Unplug the cable.** In every container terminal, including the watchdog's:
   ```bash
   ANT1_IFACE=wlp3s0 source scripts/ant1_env.sh
   ros2 topic list | grep -c $NS
   ros2 topic hz $NS/scan
   ```
   The first should be about 48 and the second about 10 Hz.
   - Restart terminals that were already running, including `ant1_watchdog` and `ant1_rviz`, because they're still bound to the cable.
5. Drive exactly as before (`ant1_watchdog` + `ant1_keys`) at **0.05 m/s**. Stay within about 10 m line-of-sight of the laptop.
   - **If the Wi-Fi drops while moving, nothing can stop the robot except the e-stop or its laser safety zone**, because the robot has no command timeout.
6. Back to cable: plug it in and run `source scripts/ant1_env.sh` (default `enp2s0`). The robot keeps both links.

| Symptom | Fix |
|---|---|
| Robot doesn't see `ant1-net` in the scan | Hotspot not running (`nmcli dev status`); keep `band bg` (2.4 GHz) |
| Ping fails | Wrong IP (check `ip neigh`); the robot didn't apply (redo Test → Apply & Restart over the cable) |
| Ping works, no topics | Forgot `ANT1_IFACE=wlp3s0` in this terminal; restart the daemon by re-sourcing |
| Topics appear but stutter | Too far or interference; move closer, close bandwidth-heavy rviz displays |

## 2. Step 2: sensors, and moving from them
| Topic (under `$NS/`) | Type | Rate | Notes |
|---|---|---|---|
| `scan` | LaserScan | 10 Hz | fused 360°, 1441 rays, **−π..π (front = middle index)**, 0.03–25 m, body already filtered |
| `scan_fl/fr/bl/br` | LaserScan | 10 Hz | raw corner STL27L lidars, 2175 rays, **with intensities** (reflective tape stands out) |
| `odom` | Odometry | 10 Hz | fused wheels + rf2o laser odometry + IMU; frames `olive_olixRobot_ant1_id001_{odom,base_link}` |
| `wheel_odom`, `wheel_rpm` | Odometry, Float32MultiArray | 14 Hz | |
| `s1/{fl,fr,bl,br,bm}/imu` | Imu | ~105 Hz | five olixSense S1 modules |
| `battery`, `system_voltage`, `ems`, `status` | | | status = CPU, disk, firmware |

All sensor topics are **BEST_EFFORT**, so subscribe with `qos_profile_sensor_data`.
- **TF** is on the **global** `/tf` (10 Hz) and `/tf_static`, not under `$NS`:
  - `odom → base_link`, then `base_link → laser` (at the robot centre).
  - `laser → laser_fl/fr/bl/br` (±0.18 m corners).
  - All frame names start with `olive_olixRobot_ant1_id001_`.
- **See it move:** `ant1_rviz`, our view in `ws/src/team_pkg/config/ant1.rviz`:
  - Top-down, following the robot, in the odom frame.
  - Shows the robot axes, a red odometry trail, and the fused lidar.
  - The raw corner lidar coloured by intensity is included but off; tick it to show it.
  - Drive with `ant1_teleop`, `ant1_drive` or `ant1_steer` (GUI sliders) and watch the trail grow while walls stay put.
- **Other apps in the image:**
  - `ros2 run plotjuggler plotjuggler`: ROS2 Topic Subscriber → `$NS/odom`. Drag `pose/position/x` and `y` together for an XY trajectory plot.
  - `rqt`: plugins Topic Monitor, Plot, Console (robot logs), Bag, TF Tree, Robot Steering.
  - `ros2 run tf2_tools view_frames`: writes a PDF of the TF tree.
  - `rqt_graph` and node lists can't see the robot's nodes from Humble.
- **Sensor-driven motion:** `python3 challenges/01_autonomous_navigation/src/obstacle_stop.py --ros-args -r __ns:=$NS`. Every standalone script with relative topics (`scan`, `odom`, `cmd_vel`) runs on the robot this way.
- **Record every run:** `ros2 bag record -o ant1_run1 $NS/scan $NS/odom $NS/cmd_vel`.
- **Lidar on/off at runtime:** `ros2 service call $NS/STL27L_bl/change_state lifecycle_msgs/srv/ChangeState "{transition: {id: 4}}"` (4 = off, 3 = on).
- **Blind spot:** the lidar sees one plane about 10 cm up. Tables, overhangs and flying drones are invisible to it; the D555 covers those.

## 3. The robot itself
- 600×400×146 mm, 18 kg, **60 kg payload**, mecanum (x, y, yaw), up to 2.5 m/s, flat top plate with M7 holes.
- 24 V 20 Ah LiFePO₄, 6–10 h of use. Charge only when stationary.
- Debian 12, firmware 3.2.0, **ROS 2 Jazzy**, CycloneDDS, domain 0. Ports: GbE with **PoE+**, USB 3.0; Wi-Fi and BT optional.
- Onboard software: Nav2, slam_toolbox, robot_localization, rf2o, waypoint_server, rosbag2 (MCAP), rosbridge, Vizanti. **No camera driver.**

## 4. Communication: protocols and ports
| Channel | Protocol / port | For |
|---|---|---|
| ROS 2 | DDS/RTPS over UDP. Domain 0 discovery is multicast `239.255.0.1:7400`, data is unicast 7410+. | Everything ROS. Humble ↔ Jazzy works at the topic level. |
| rosbridge | JSON over WebSocket, **`ws://192.168.7.100:5001`** | Machines without ROS (Python, JS, dashboards) |
| Web UI | http://192.168.7.100 (:80) | Status, joystick, Wi-Fi setup, SLAM and nav buttons |
| Vizanti | http://192.168.7.100:5000 | Web map, costmap and path viewer |
| File Browser | http://192.168.7.100:9090 | Download maps and bags from the robot |
| SSH | :22 (user `olive`) | **Only with mentor approval** |

**Sharing data with teammates (later):**
- Same network plus `ROS_DOMAIN_ID=0` and CycloneDDS: they see everything natively.
- Venue Wi-Fi often blocks multicast. Then use Cyclone unicast peers, a travel router (most reliable), a zenoh bridge (`zenoh-bridge-ros2dds`), or rosbridge.
- Raw depth images (~25 MB/s) are too much for Wi-Fi. Send compressed images or only results.

## 5. Gotchas
- **Lidars stuck "inactive" after power-on** (happened 10 Oct when it was powered on without holding the e-stop):
  - Symptoms: no `scan` data, all `STL27L_*` in lifecycle state 2, `change_state` activate returns `success=False`, and the Web UI allows only manual driving.
  - Fix: power-cycle **with the e-stop pressed for ~10 s after power-on**, then release. Check with `ros2 service call $NS/STL27L_fl/get_state lifecycle_msgs/srv/GetState "{}"`, which should say `active`.
- **While the e-stop is pressed:** `battery` and `system_voltage` read 0, `wheel_odom` drops to about 1 Hz, and the LEDs ignore user colours. All of this is normal. After release, readings return (verified 10 Oct: 67 %, 26.0 V, wheel_odom 13 Hz, LED red/green OK).
- **No cmd_vel timeout:** the robot keeps executing the last command forever (verified 10 Oct, needed the e-stop). Always:
  - run `ant1_watchdog` (it sends STOP after 0.5 s without commands);
  - stream commands at 5 Hz or more;
  - end every motion with a zero Twist;
  - send a zero Twist **before** releasing the e-stop.

  Our nodes (`ant1_keys`, `ant1_drive`) send zeros on exit, Ctrl-C, closed terminal, or `docker stop`. Nothing on the laptop can help if the laptop or the network dies, so the e-stop stays in reach.
- `serdata.cpp:384 ... not null-terminated` spam is Humble failing to parse Jazzy discovery metadata. It's harmless and data is fine.
- `ros2 node list`, `ros2 param get` and `ros2 node info` can't see robot nodes from Humble. Use `ant1_param` (parameter services), or rosbridge's `rosapi/nodes`.
- The **robot clock is ~21 days behind** (reads 19 Sep 2026). Goals and poses you send it should use `stamp = 0` ("latest").
- Nav2 action types differ between Humble and Jazzy. Prefer topics (`$NS/goal_pose`) or the waypoint services over Nav2 actions from Humble.
- After network changes, if topics seem stuck: `pgrep -f "ros2cli.daemon|ros2-daemon" | xargs -r kill -9; rm -rf ~/.ros/daemon; ros2 daemon start`.

## 6. What comes next (outline)
1. **Map and navigate:**
   - Web UI → SLAM → Mapping. Clone `github.com/olive-robotics/olvx_g1` into `ws/src` for `waypoint_server_interfaces` and the rviz configs.
   - Waypoint services: `$NS/save_waypoint`, `list_waypoints`, `move_to_waypoint`, `delete_waypoint`, `save_waypoint_pose`.
2. **Explore:** frontier exploration on SLAM + Nav2.
3. **RealSense D555:**
   - Depth up to 1280×720@90, RGB 1280×800@60, global shutter, IMU, IP65. Connects by PoE (default IP `192.168.11.55`, MTU 9000) or USB-C.
   - Use Intel's `realsense2_camera` driver (librealsense ≥ 2.56.4, built with DDS for Ethernet). It runs on a laptop riding the robot, or on the robot only if SSH is allowed.
   - Enables YOLO + depth → 3D target → Nav2, RTAB-Map 3D mapping, 3D obstacles, AprilTags, and seeing drones.
4. **Crazyflie landing mission:**
   - A laptop with a Crazyradio runs crazyswarm2 and bridges the ANT1 pose (DDS) to drone `go_to`/`land`.
   - With a Flow deck, positions are relative to takeoff, so take off from the ANT1 and land while it is stationary.
   - With Lighthouse, align its frame with `map` once.
   - Later, the ANT1 finds the drones: AprilTag or LED deck plus D555 depth.
